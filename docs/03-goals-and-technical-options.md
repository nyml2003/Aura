# 目标与技术选型参考

本文档记录**希望达成的目标**以及**技术选型与方案参考**。硬性约束见 [02-constraints.md](./02-constraints.md)，产品需求见 [01-product-requirements.md](./01-product-requirements.md)。

---

## 一、目标（希望达成的结果）

- **部署**：Docker 编排，一条命令/脚本可在 2C2G 上跑起；Nginx 反向代理，Go 专注 API。
- **架构**：单体、区分网关层，保留扩展微服务可能；**URL/路由/跳链由研发设计**，链接由后端下发**完整 URL**，前端不拼接。
- **前端**：**Monorepo + 多 npm 包**，如请求 SDK（交互与非首屏数据请求）、页面通用依赖（从 window 解析数据并渲染）；各页面应用依赖上述包，见 [06-MVP 方案](./06-mvp-plan.md)。
- **内容**：Item 抽象（文章 + 小游戏等）；首页推荐 + 瀑布流，列表分页查询；正文与媒体存储见下文。
- **体验**：首屏从输入 URL 到页面不抖动为止约 100ms；布局与页面数据同时下发，由 Go 内 BFF 式模块拼装后内联进 HTML，不 SSR、不引入 Node。详见 [04-可行性评估](./04-product-tech-feasibility.md)。
- **质量**：除视图层外单测覆盖；OpenAPI 契约；E2E 覆盖主流程（技术设计里定范围）。
- **运维**：日志异步写、可过期、可排查；单独运维前后端；健康检查；CI 发布；尽量零停机；备份与内容存储方案一致。
- **安全**：RBAC、私密/草稿、隐藏登录入口、基础防护。

---

## 二、服务形态 · 业界考量

- **先做单体**：在边界还不清晰、流量与团队规模有限时，先做单体能减少分布式带来的运维与一致性成本。博客场景 2C2G，单体足够。
- **区分网关层**：指**代码内的分层**。入口/网关层做鉴权、限流、请求校验、路由到业务；业务层不依赖 HTTP 细节，可单测；将来若要拆微服务，入口层可整体迁成独立网关。

---

## 三、博文内容存储与运维（选型参考）

- **成本优先**：同机目录（如 `data/uploads/images/`），备份随主机；URL 可配置前缀，后续接 CDN 只改配置。可选：缩略图由后端或 CI 生成。
- **进阶**：量或带宽上来再迁 OSS + CDN，应用层抽象「媒体 URL 生成」便于切换。
- **视频**：成本优先则**不自建**，用外链嵌入（B 站、YouTube 等），文章里只存 URL。
- **CDN**：静态与媒体用可配置的域名/路径前缀（如 `STATIC_CDN_URL`、`UPLOAD_CDN_URL`），部署时配置即可。

---

## 四、小结

- **媒体**：图片与文件先同机目录，URL 可配置前缀以便后续接 CDN/OSS；视频用外链嵌入。
- **先同机目录**；URL 可配置前缀，后续切 OSS 或接 CDN 只改配置。
- **成本**：按流量+请求计费，个人博客小流量月费通常很低；URL 设计成可配置域名/前缀即可平滑接 CDN。
