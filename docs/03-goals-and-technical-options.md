# 目标与技术选型

本文档说明博客系统的**技术目标、约束**以及**技术选型与理由**，与 [01-product-requirements.md](./01-product-requirements.md) 中的产品需求与非功能目标对应。URL/路由与链接规则见 [09-url-routing-and-links.md](./09-url-routing-and-links.md)，前后端 API 契约见 [10-api-contract.md](./10-api-contract.md)。

---

## 一、目标与约束

### 1.1 技术目标


| 维度        | 目标                    | 说明                                                          |
| --------- | --------------------- | ----------------------------------------------------------- |
| **首屏体验**  | 从输入 URL 到页面可交互 ≤200ms | 关键路径（首页、列表、详情等）一次到位，不做骨架屏；达标方式为首屏数据与 HTML 一起下发（SSR + 数据注入）。 |
| **数据与交互** | 支持复杂交互 + 数据实时性        | 前端可做分页、筛选、搜索等；后端数据持续更新时，首屏拿最新数据，后续交互通过接口获取最新数据。             |
| **运行环境**  | 适配轻量服务器               | 2 核 2G vCPU、40G 云盘、3M 公网带宽；控制内存/CPU，避免 SSR 与带宽过载。           |
| **工程化**   | 工具链可自主维护              | 优先保障性能与可控性；可选用小众技术，不依赖成熟生态，无协作/排障风险。                        |


### 1.2 关键约束


| 约束        | 具体限制               | 对技术选型的影响                    |
| --------- | ------------------ | --------------------------- |
| **服务器资源** | 2 核 2G、40G 盘、3M 带宽 | 控制内存与 CPU，减少 SSR 压力与网络传输量。  |
| **性能指标**  | 首屏可交互 ≤200ms       | 压缩服务端渲染、网络传输、前端解析与执行各环节耗时。  |
| **数据特性**  | 后端数据实时变化           | 首屏用实时数据，后续交互可再请求，不能依赖纯静态生成。 |
| **维护方式**  | 自主维护、小众无风险         | 可选性能最优方案，不必迁就生态成熟度。         |

## 二、技术选型

选型原则：**性能与资源适配优先于生态**。

### 2.1 选型结论概览


| 技术层       | 选型                           | 淘汰方向（简述）                                                        |
| --------- | ---------------------------- | --------------------------------------------------------------- |
| **前端**    | SolidJS / SolidStart         | React/Angular 内存与 SSR 开销大；Vue 虚拟 DOM 有运行时成本；Svelte 性能略逊于 Solid。 |
| **后端**    | Go (Gin)                     | Java 在 2 核 2G 上启动慢、占内存；Python 并发与响应易成瓶颈；Node 内存易溢出。             |
| **数据库**   | SQLite                       | MySQL/PostgreSQL 默认配置占内存，轻量机上不经济。                               |
| **渲染策略**  | SSR + 首屏数据注入 window + 前端异步更新 | 纯 CSR 首屏慢；纯 SSG 无法满足数据实时；纯 SSR 需配合数据复用与缓存以控压。                   |
| **部署/缓存** | Nginx 反向代理 + Redis 轻量缓存      | 微服务与多中间件（MQ/ES）在 2 核 2G 上不适用。                                   |


注：当前 MVP 若采用 Deno + Solid + SSR（见 [06-mvp-plan.md](./06-mvp-plan.md)、[08-pipeline-and-roles.md](./08-pipeline-and-roles.md)），以跑通链路为主；上述选型可作为后续演进或另一实现路径的参考。

### 2.2 选型理由摘要

- **SolidJS/SolidStart**：无虚拟 DOM、细粒度响应式，编译期生成 DOM 操作，SSR 与包体表现优于 Svelte；语法接近 React，迁移成本低；生态虽小但可自封装组件与工具。
- **Go (Gin)**：内存占用低（通常 <100MB）、接口响应快（<10ms 级），适合 2 核 2G；仅提供 JSON API 时 CPU 占用可控。
- **SQLite**：零独立部署，嵌入应用即可；开启 WAL 后读写性能满足轻量场景与数据实时更新。
- **SSR + 首屏注入 + 异步更新**：首屏由服务端输出完整 HTML 与实时数据，满足 200ms 目标；首屏数据注入 `window.__INIT_DATA__`（或与 [10-api-contract.md](./10-api-contract.md) 约定一致），前端复用、不重复请求；分页/刷新等通过异步接口拿最新数据。
- **Nginx + Redis**：Nginx 做反向代理与压缩（Gzip/Brotli），可缓存 SSR 结果与静态资源；Redis 缓存高频接口数据，平衡性能与实时性。具体缓存策略在 MVP 后与「搜索、管理后台」一并约定。

## 三、技术栈与配置要点

### 3.1 核心技术栈


| 技术层       | 选型                   | 配置/优化要点                                                                           |
| --------- | -------------------- | --------------------------------------------------------------------------------- |
| **前端**    | SolidJS / SolidStart | SSR 模式；构建阶段压缩与 Tree-shaking；首屏数据注入 `window.__INIT_DATA__`，与 API 契约一致；按需封装基础组件与工具。 |
| **后端**    | Go (Gin)             | 生产关闭调试日志；接口仅返回 JSON；限流（如 50 并发）；与 SQLite/Redis 配合。                                |
| **数据库**   | SQLite               | 开启 WAL；连接池控制（如最大连接数 2）；备份/恢复脚本自维护。                                                |
| **渲染策略**  | SSR + 首屏注入 + 异步更新    | 服务端按路由取数并渲染 HTML；客户端从 `__INIT_DATA__` 复用数据并 hydrate；后续交互走 API。                    |
| **部署/缓存** | Nginx + Redis        | Nginx 反代前端 SSR 与后端 API；SSR 与静态资源缓存策略；Redis 内存与淘汰策略（如 200MB、allkeys-lru）。          |


### 3.2 性能目标（全链路）


| 环节           | 目标耗时       | 手段              |
| ------------ | ---------- | --------------- |
| 服务端取数        | <40ms      | 减少查询、Redis 缓存命中 |
| 服务端渲染 HTML   | <15ms      | 精简 SSR 逻辑与依赖    |
| 网络（Nginx 返回） | <20ms      | 压缩、缓存           |
| 浏览器解析 + 注入数据 | <30ms      | 注入脚本优先、数据格式简洁   |
| 前端初始化（复用数据）  | <40ms      | 减少非必要计算         |
| **全链路**      | **<145ms** | 留出相对 200ms 的余量  |


### 3.3 资源占用（2 核 2G 参考）


| 组件     | 内存          | CPU（峰值）  |
| ------ | ----------- | -------- |
| SSR 服务 | ≤500MB      | ≤20%     |
| Go API | ≤100MB      | ≤15%     |
| Redis  | ≤200MB      | ≤5%      |
| Nginx  | ≤50MB       | ≤5%      |
| 系统及其他  | ≤500MB      | ≤5%      |
| **合计** | **≤1350MB** | **≤50%** |


### 3.4 工程化建议

- **配置与运维**：固化 Nginx、应用、Redis 的配置模板与一键启停脚本。
- **排障**：统一日志与错误记录，便于自主排查。
- **版本**：锁定依赖版本，按需再升级。
- **监控**：对 CPU、内存、带宽做简单监控与告警。

---

## 四、小结

- **性能**：全链路首屏可交互目标 <145ms，满足 200ms 要求，并适配 2 核 2G 资源。
- **数据**：首屏用实时数据，后续交互异步更新，兼顾速度与实时性。
- **可控**：技术栈可自主维护，不依赖社区生态。
- **前端**：语法接近 React，迁移与扩展成本可控；当前阶段前端以**独立应用**先跑通为主，详见 [README.md](./README.md) 中的元方案与后续约定。
