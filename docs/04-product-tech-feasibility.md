## 二、首屏约 100ms：输入 URL 到页面不抖动为止（有风险）

- **产品要求**：关键路径（首页、列表、文章详情、游戏/demo 详情、搜索等）的体验目标为——**从用户输入 URL 到页面稳定、不再发生布局抖动** 尽量在约 100ms 内完成。
- **指标含义**：计时起点 = 输入 URL（或发起请求）；终点 = 页面渲染完成且无后续布局变化（不抖动）。骨架屏会先出占位再替换为真实内容，属于**页面元素变更**，对「到不抖动为止」没有优化空间，故**不采用骨架屏**。
- **风险**：若采用**纯 CSR + 首屏再请求接口**，会经历「HTML/JS 加载 → 请求接口 → 渲染数据」两段，难以做到 100ms 内；且 RTT + 接口 + 渲染 叠加，时间易超标。

### 推荐方案：Go 内 BFF 式拼装 + 数据内联进 HTML

- **数据与 HTML 一起返回**：用户请求某 URL 时，**不**走「先返空壳 HTML → 前端再请求接口 → 再渲染」；改为**同一次响应**里就带上首屏所需全部数据（布局相关 + 当前页数据），前端一次渲染即稳定。
- **实现形式**：**首屏数据内联**——Go 返回的 HTML 中内联首屏 JSON（如 `<script type="application/json" id="__INIT_DATA__">`），内容即「页面 payload」；前端首屏直接读该数据渲染，不再发首屏接口。Nginx 将页面 URL 反向代理到 Go，Go 根据 path 选择模板 HTML + 拼装对应模块数据并注入后返回。
- **边界**：**前端**：只负责用下发的数据渲染、交互；不拼链接、不决定「这一页要哪几个模块」。**后端**：按 URL/路由决定要哪些模块、拼好数据、注入 HTML；模块注册与拼装逻辑在 Go 内，保持前后端边界清晰。
- **「约 100ms」**：从**输入 URL** 到 **页面首屏渲染完成且不再发生布局变化（无 CLS）** 的时延，目标约 100ms 内。
- 从输入 URL 到页面**不再抖动**约 100ms 内完成；首屏**一次成型**，布局数据与页面数据**同时下发**，前端一次渲染即稳定。

## 三、必须落地的清单

技术方案要**真正**满足产品诉求，需要在技术设计阶段完成以下项，否则会有缺口：

1. **首屏 100ms**：Go 内 BFF 式模块划分与拼装、数据内联进 HTML 的格式与流程；验收标准（含目标环境、RTT 假设）。
2. **小游戏/demo** 承载与性能边界。
3. **搜索**方案与资源。
4. **推荐打标**存储与 API。
5. **链接与路由**：站点根、路径规范、开发/部署环境区分；响应结构（href、backUrl 等，**均为完整 URL**）与示例；前端路由与后端链接的对应关系。
6. **运维**：若运维前端为必做则功能范围与排期；若为可选则一期仅日志接口 + 健康检查，运维前端二期。

## 四、结论

| 维度 | 结论 |
|------|------|
| **整体** | **当前技术设计能支撑产品目标**，在 2C2G 单机、单实例、无外网 DB、Docker + Nginx + Go + React MPA 的约束下，可实现：item 抽象、首页推荐瀑布流、分页列表、文章/游戏详情、搜索、管理端 CRUD 与推荐打标、链接由后端维护（**完整 URL**）、RBAC 与隐藏登录、日志/健康/CI/备份等。 |
| **必须落地的** | 技术设计阶段需明确：① **100ms 首屏**（Go 内 BFF 式模块拼装 + 数据内联进 HTML）；② **小游戏/demo** 承载与性能边界；③ **搜索**方案与资源；④ **推荐打标**存储与 API；⑤ **链接生成规则**（下发完整 URL）与响应结构；⑥ **运维**前端是否必做。 |
