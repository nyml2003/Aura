# 前后端 API 契约

本文档约定前后端之间的**数据与接口形态**：首屏数据、列表/详情等 API 的通用结构，以及**链接在响应中的位置**。Item 的领域模型（字段定义、类型枚举等）**后续在本文档内补充**；管理后台、搜索、缓存等接口在 MVP 完成后另行约定。

---

## 一、通用约定

- **数据格式**：JSON。
- **字符编码**：UTF-8。
- **错误响应**：HTTP 状态码 + 可选 JSON body，例如 `{ "error": "code", "message": "..." }`；具体错误码与字段 MVP 阶段可简化，后续统一。
- **链接**：凡需前端跳转的链接，均由后端以**完整 URL** 字符串形式提供，字段命名见下；前端不做 host/path 拼接。URL 规则见 [09-url-routing-and-links.md](./09-url-routing-and-links.md)。

---

## 二、首屏数据（SSR 注入）

### 2.1 注入位置与名称

- 首屏数据由后端在 SSR 时注入到页面，供前端 hydrate 使用。
- 注入名称约定为 **`window.__INIT_DATA__`**（或与现有实现一致的等效名称）。
- 内容为**单一大对象**，结构按「场景」区分。

### 2.2 通用首屏结构（按 scenecode）

首屏数据的**顶层**建议包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| `scene` | string | 场景码，与路由/scenecode 对应，如 `home`、`list`、`article`、`item`、`search` |
| `payload` | object | 本场景的数据；结构见各场景约定 |

即形如：`{ "scene": "list", "payload": { ... } }`。  
若现有实现已采用扁平结构（如直接把 `list` 等放在顶层），也可保留，但需在本文档中注明，前后端统一。

### 2.3 各场景 payload 形态（概要）

- **list**：列表页。`payload` 中至少包含当前页的**条目列表**与**分页/链接信息**；每条条目含**详情链接**（完整 URL）。Item 具体字段（id、title、summary、type 等）**后续补充**。
- **home**：首页。`payload` 中为推荐条目列表等，结构可与 list 类似或简化；条目含详情链接。
- **article / item**：详情页。`payload` 中为当前文章或小游戏/demo 的**单条数据**及**返回链接**（首页、列表等完整 URL）。Item 详情字段**后续补充**。
- **search**：搜索。MVP 后约定；形态上可为「带关键词与筛选的列表 + 分页链接」。

列表与详情中的「链接」字段命名见下节。

---

## 三、链接在响应中的位置

### 3.1 列表项

- 每个列表项（文章/小游戏/demo）至少包含一个**跳转至详情页的链接**。
- 字段名约定：**`href`** 或 **`url`**（全项目二选一，统一即可），值为完整 URL 字符串。
- 示例：`{ "id": "...", "title": "...", "href": "https://mysite.com/article/hello-world" }`  
  Item 的其余字段（type、summary、meta 等）**后续在 Item 领域模型中补充**。

### 3.2 分页

- 列表/搜索等分页数据中，若有「上一页」「下一页」「第 N 页」等，建议以**链接**形式下发，便于前端直接使用。
- 字段名建议：`links.prev`、`links.next`、`links.pages[N]`，或扁平结构 `prevHref`、`nextHref`；具体在确定列表 API 时定一版即可。
- 值均为**完整 URL**。

### 3.3 详情页与导航

- 详情页首屏 payload 中应包含**返回入口**的完整 URL，例如：首页、列表页、可选「上一项/下一项」。
- 字段名建议：`links.home`、`links.list`、`links.prev`、`links.next` 等，或与前端约定为一组 `nav` 对象。

---

## 四、异步 API（非首屏）

- **列表**：若存在独立列表接口（如 `GET /api/items` 或 `GET /api/list`），响应体应包含条目数组 + 分页信息；每条条目含 **href/url**（完整 URL）；分页链接同上。Query 参数（page、size、type、tag 等）与 [09-url-routing-and-links.md](./09-url-routing-and-links.md) 中 query 约定一致。
- **详情**：若存在独立详情接口（如 `GET /api/items/:id`），响应体为单条 Item + 可选 `links`（返回首页、列表等）。
- **搜索**：MVP 后约定；形态上可为列表 + 分页链接，参数与 path 与 09 一致。

以上接口的 **URL 路径、方法、请求参数** 可在实现时再定一版，本文档仅约定：**凡需跳转的均为完整 URL，且 Item 相关字段在领域模型文档中补充**。

## 五、Item 领域模型（待补充）

- **类型枚举**：如 article、game、demo 等，后续在本文档或独立「数据模型」文档中列出。
- **列表项字段**：id、type、title、summary、href/url、meta（如日期）、可选 tag 等；是否必填、类型、命名统一在此补充。
- **详情项字段**：在列表项基础上扩展正文、媒体、配置等；与首屏 payload 及详情 API 一致。
- **推荐/状态等**：如「推荐到首页」、发布状态等，若影响接口形态，一并在此或管理后台契约中约定。

上述补充完成后，前后端类型定义（TypeScript/Go 等）与本文档保持同步。

## 六、与 MVP 的对应

- **当前阶段**：以首屏 SSR + `__INIT_DATA__`（或等效）为主；列表页至少约定 list 的 payload 结构及条目的 **href/url**。
- **管理后台、搜索、缓存** 相关接口与数据结构，在 **MVP 版本完成后再约定**，可在本文档中新增章节或单独文档。
